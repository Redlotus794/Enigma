# 产品愿景与业务目标

> 本文档定义 enigma-demo 的战略定位，回答"产品为什么存在"。

## 产品名称

enigma-demo

## 服务对象

`enigma-demo` 服务于 Enigma 框架相关使用者与维护者。

| 用户群体 | 用户画像特征 | 核心诉求 |
|----------|--------------|----------|
| Enigma 框架使用者 | 正在学习或评估 Enigma 框架的后端开发者、架构师 | 通过可运行样例理解标准业务项目如何组织代码 |
| 后端开发者 | 关注 DDD、Spring Boot、Java 8 工程实践 | 参考业务规则在领域模型中的表达、验证和演进方式 |
| 框架维护者 | 维护 Enigma starter 与示例工程的开发人员 | 通过 demo 验证 starter 的核心能力是否可用、易用、可解释 |

## 解决的问题

当前 Enigma 缺少一个从零设计、围绕明确业务规则组织的小型完整样例，导致使用者难以直接判断：

1. 如何基于 `enigma-ddd-spring-boot-starter` 创建标准业务项目。
2. 如何避免把示例写成面向数据库表的贫血 CRUD。
3. 如何在代码中清晰表达业务对象、业务动作和业务规则。
4. 如何用测试证明非法业务操作会被明确拒绝。

## 核心业务价值

- 提供一个小而完整的业务样例，展示 Enigma DDD 项目的推荐组织方式。
- 通过"特别任务支援科成员养成与任务准备"场景，让业务规则比技术脚手架更容易被观察。
- 用角色状态、装备栏、导力器配置三个业务对象展示领域行为、约束校验和测试覆盖。
- 为后续 Enigma 使用文档、示例代码和 starter 能力验证提供统一参照。

## 成功标准

| 指标 | 目标值 | 衡量方式 |
|------|--------|----------|
| MVP 场景完整度 | 覆盖角色创建、状态查看、状态调整、装备更换、导力器配置 | README、接口或测试用例能串联展示完整流程 |
| 业务规则可见性 | 每条基础业务规则都有明确代码表达 | 领域对象或领域服务中可直接定位校验逻辑 |
| 非法操作拒绝能力 | PRD 中列出的非法操作均被拒绝 | 单元测试或模块级测试覆盖异常路径 |
| 运行可验证性 | 模块级 Maven 测试通过 | 执行 `mvn test` 或 `mvn verify` |
| 示例可解释性 | 使用者能通过 README 理解业务范围和运行方式 | README 包含业务说明、运行命令和关键代码导航 |

## 产品边界（Scope）

**包含（In Scope）：**

- 特别任务支援科成员的角色状态管理。
- 武器、防具、两个饰品栏位的装备与卸下。
- 1 个核心回路槽位和 7 个普通回路槽位的导力器配置。
- 非法创建、非法状态调整、非法装备栏位、非法导力器槽位等异常操作拒绝。
- 业务规则测试。

**不包含（Out of Scope）：**

- 完整游戏系统、剧情、任务流转、战斗结算和地图探索。
- 复杂数据库、中间件或外部系统依赖。
- 通用脚手架生成器能力。
- Enigma 所有 starter 能力演示。
- 多角色队伍编成、物品库存、回路属性加成计算等后续可扩展能力。

## 竞品参考

| 参考对象 | 核心优势 | 可借鉴点 |
|----------|----------|----------|
| `java-spring-boot-ddd-example` | 标准 DDD 示例项目 | 模块组织、分层表达和 README 导航方式 |
| Spring Boot 官方示例 | 可运行、轻量、便于学习 | 示例应保持小范围、少依赖、容易启动 |
| 典型 RPG 角色准备流程 | 角色状态、装备、能力配置概念清晰 | 以玩家熟悉的业务动作承载领域规则 |

## 战略结论

第一阶段只围绕"角色执行支援任务前的准备情况"建模，优先保证角色状态、装备栏和导力器配置的业务语言清晰、规则可测试、代码可运行。任何不能直接支撑该目标的能力均延后。
