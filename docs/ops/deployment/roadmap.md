# Enigma 版本发布路线图

## 1. 目标

本路线图用于管理 Enigma `2.0.0` 版本从开发、集成、候选发布到正式发布的推进过程，明确各分支职责、阶段准入条件、验证要求和发布产物。

## 2. 当前基线

更新时间：2026-07-23

| 项目 | 当前状态 |
|------|----------|
| 正式发布基线 | `1.1.1-RELEASE` |
| 稳定分支 | `main` |
| 2.x 集成分支 | `develop-2.x.x`，已完成 `dev/2.0.0` squash 合并 |
| 2.0.0 开发分支 | `dev/2.0.0` |
| 2.0.0 发布分支 | `release/v2.0.0`，已从 `develop-2.x.x` 创建 |
| 目标版本 | `2.0.0` |
| 目标发布日期 | 待确定 |

> 当前各模块 `pom.xml` 已统一为 `2.0.0-SNAPSHOT`。完成 release 验证后，再统一切换为正式版本 `2.0.0`。

## 3. 分支职责

| 分支 | 职责 | 允许进入的内容 |
|------|------|----------------|
| `main` | 保存已验证、可发布的稳定版本 | 正式发布合并、紧急修复 |
| `develop-2.x.x` | 集成和验证 2.x 版本全部变更 | 经整理的功能提交、缺陷修复、版本与文档更新 |
| `dev/2.0.0` | 汇总 2.0.0 开发阶段变更 | 2.0.0 功能开发和重构 |
| `release/v2.0.0` | 冻结功能并完成发布验证 | 发布阻断缺陷修复、版本号、发布文档和配置修正 |

## 4. 发布路径

```text
dev/2.0.0
    │  squash 为一个可审查提交
    ▼
develop-2.x.x
    │  集成验证通过
    ▼
release/v2.0.0
    │  发布验证通过，版本切换为 2.0.0
    ▼
main
    │  创建 v2.0.0 标签并发布制品
    ▼
2.0.0
```

正式发布完成后，将发布结果同步回 `develop-2.x.x`，并根据下一迭代计划切换到新的 `SNAPSHOT` 版本。

## 5. 阶段计划

### 阶段一：整理 2.0.0 开发变更

状态：已完成（2026-07-23）

- 核对 `dev/2.0.0` 相对 `develop-2.x.x` 的完整变更范围。
- 清理临时文件、无关提交和不应进入 2.0.0 的内容。
- 将 `dev/2.0.0` 的有效变更 squash 为一个语义完整、可审查的提交。
- 在提交说明中概括功能、兼容性影响、迁移要求和验证结果。

退出条件：

- squash 后的提交范围清晰且无无关文件。
- 变更能够干净应用到 `develop-2.x.x`。
- 代码和文档评审范围已确认。

### 阶段二：集成到 develop-2.x.x

状态：已完成（2026-07-23）

- 将阶段一的 squash 提交合入 `develop-2.x.x`。
- 统一所有 Maven 模块版本为 `2.0.0-SNAPSHOT`。
- 同步更新 `README.md`、模块说明和 `CHANGELOG.md`。
- 检查模块依赖边界、BOM 版本管理和 Java 8 兼容性。

退出条件：

- 所有版本承载文件保持一致。
- 目标模块测试和根级 Maven 验证通过。
- JaCoCo 覆盖率达到各模块配置要求。
- 无未处理的发布阻断问题。

### 阶段三：创建 release/v2.0.0

状态：进行中（2026-07-23 已创建分支）

- 从验证通过的 `develop-2.x.x` 创建 `release/v2.0.0`。
- 冻结新功能，只接受发布阻断缺陷修复。
- 完成升级说明、兼容性说明、配置清单和回滚方案。
- 在候选发布验证期间保持版本为 `2.0.0-SNAPSHOT`；正式发布前统一切换为 `2.0.0`。

退出条件：

- 全量构建、单元测试和集成测试通过。
- 发布制品能够在目标 Maven 仓库中正确解析。
- 发布说明、变更记录、升级步骤和回滚步骤完成评审。
- 发布负责人确认可进入正式发布。

### 阶段四：正式发布 2.0.0

状态：未开始

- 将 `release/v2.0.0` 合入 `main`。
- 确认所有模块版本均为 `2.0.0`。
- 在 `main` 创建签名或受保护标签 `v2.0.0`。
- 使用项目指定的 Maven settings 发布制品到 Nexus。
- 验证 BOM、Parent 和各 Starter 制品可被示例项目正常引用。

退出条件：

- GitHub 上的 `main`、发布提交和 `v2.0.0` 标签一致。
- Nexus 中全部目标制品发布成功且可下载。
- `CHANGELOG.md` 记录正式发布日期和最终变更摘要。
- 发布结果、验证证据和已知风险完成归档。

### 阶段五：发布后收尾

状态：未开始

- 将正式发布结果同步回 `develop-2.x.x`。
- 关闭或归档 `release/v2.0.0`。
- 根据后续计划将开发版本切换为新的 `SNAPSHOT`。
- 跟踪发布后的兼容性反馈和紧急缺陷。

## 6. 发布验证清单

### 代码与构建

- [ ] Java、Maven 和 Maven Wrapper 版本符合项目要求。
- [ ] Maven 模块版本及内部依赖版本保持一致。
- [ ] `mvn clean verify` 执行成功。
- [ ] 单元测试、集成测试及覆盖率检查通过。
- [ ] 未引入不符合模块职责和 DDD 分层边界的依赖。

### 文档与版本

- [ ] `README.md` 与各模块说明反映 2.0.0 的实际能力。
- [ ] `CHANGELOG.md` 包含新增、修改、修复、废弃及发布日期。
- [ ] 升级说明列出破坏性变更和迁移方法。
- [ ] 发布操作和验证结果记录到 `docs/ops/log/`。

### 制品与回滚

- [ ] Nexus 发布目标和账号环境已现场确认。
- [ ] BOM、Parent、Core 和各 Starter 制品齐全。
- [ ] 示例项目完成依赖解析和启动验证。
- [ ] 已记录上一稳定版本及回滚步骤。
- [ ] 发布失败时不覆盖已发布的 RELEASE 制品。
