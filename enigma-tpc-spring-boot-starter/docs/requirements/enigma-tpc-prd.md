# enigma-tpc PRD

## 1. 背景

`enigma-tpc-spring-boot-starter` 是 Enigma 的第三方中心 Starter，面向业务系统提供统一的第三方请求接入、发送、状态跟踪、结果留痕和运维处理能力。

当前 PRD 参考项目：

- `/Users/wangjialong/codebase/dcs-global-vehicle/dcs-tpc-starter`

参考项目已具备第三方请求模型、请求类型注册、第三方社群注册、发送器注册、同步/异步发送、批量发运计划、请求状态维护、投递结果落库和运维控制接口等能力。`enigma-tpc` 需要在 Enigma 技术栈和 DDD 规范下抽象这些通用能力，形成可复用 Starter。

## 2. 产品定位

`enigma-tpc` 是第三方请求编排中心，不直接承载具体业务规则，也不绑定某一个第三方平台。业务系统通过扩展请求类型、请求模型、第三方社群和发送器，将不同第三方服务的调用过程纳入统一生命周期管理。

## 3. 目标用户

- 业务应用开发者：定义具体第三方请求类型、请求载荷、发送器和回调处理。
- 平台框架维护者：维护 Starter 的公共模型、状态机、自动装配、持久化扩展点和规范。
- 运维与支持人员：查询第三方请求执行状态，处理失败请求、重发请求和人工状态修正。

## 4. 产品目标

- 提供统一的第三方请求生命周期，从创建、待发送、已发送、已接收、已完成到异常结束。
- 支持业务系统按请求类型路由到对应第三方社群，再由社群选择具体发送器。
- 支持单个请求同步发送和异步发送，并记录发送结果。
- 支持第三方社群制定批量发运计划，按计划顺序处理多个请求。
- 提供请求重置、重发、人工设置状态等基础运维能力。
- 对每次第三方投递结果进行结构化留痕，便于问题追踪和审计。

## 5. 非目标

- 不负责具体第三方 API 协议、鉴权、报文签名和字段映射规则。
- 不内置具体业务请求类型，例如车辆、订单、用户等业务对象。
- 不提供面向终端用户的业务页面。
- 不承担领域核心业务规则，业务成功判定由发送器或回调逻辑给出。
- 第一阶段不设计复杂调度平台，只提供可被业务定时任务调用的发运计划能力。

## 6. 核心概念

| 概念 | 说明 |
|------|------|
| 第三方请求 | 一次待发送到第三方系统的业务请求，包含请求 ID、请求类型、请求载荷、状态和执行信息 |
| 请求类型 | 业务系统定义的请求分类，用于决定请求应交给哪类第三方社群处理 |
| 请求载荷 | 业务系统传入的请求数据模型，需要支持序列化保存和反序列化恢复 |
| 第三方社群 | 一组第三方发送能力的抽象，负责接收请求并选择发送器 |
| 发送器 | 执行具体第三方调用的扩展点，负责发送请求、返回响应并处理回调 |
| 发运计划 | 第三方社群生成的一组待发送请求队列，可按顺序批量执行 |
| 投递结果 | 每次发送后的结果记录，包含第三方社群、发送器、请求 ID、响应结果和异常信息 |

## 7. 业务流程

### 7.1 请求创建流程

1. 业务系统生成第三方请求 ID。
2. 业务系统选择请求类型并组装请求载荷。
3. TPC 创建第三方请求，初始状态为 `WAIT`。
4. TPC 记录请求时间、执行次数、业务成功标记和备注等执行信息。

### 7.2 单请求发送流程

1. 调用方提交请求 ID 和发送模式。
2. TPC 根据请求 ID 查询第三方请求。
3. TPC 根据请求类型找到对应第三方社群。
4. 第三方社群接收请求并返回具体发送器。
5. TPC 将请求状态从 `WAIT` 变更为 `STAND_BY`，并累计执行次数。
6. 发送器执行第三方调用并返回响应。
7. TPC 接收响应后将请求状态变更为 `RECEIVED`。
8. 发送器执行回调处理，设置业务成功标记。
9. TPC 将请求状态变更为 `COMPLETED`。
10. TPC 保存请求最新状态和投递结果。

### 7.3 异常发送流程

1. 发送过程任一阶段发生异常时，TPC 将请求状态变更为 `ERROR`。
2. TPC 记录异常发生阶段、异常编码、异常消息和响应数据。
3. TPC 仍需尽可能保存请求状态和投递结果。
4. 当持久化失败时，TPC 应记录足够的日志信息，便于人工排查。

### 7.4 异步发送流程

1. 调用方选择异步模式后，TPC 启动后台发送任务。
2. TPC 立即向调用方返回异步受理成功响应。
3. 后台任务按单请求发送流程执行。
4. 如果发送器超过配置的超时时间未完成，TPC 记录发送器超时结果。

### 7.5 批量发运计划流程

1. 业务系统或定时任务选择一个第三方社群执行发运计划。
2. 第三方社群生成一个或多个发运计划，每个计划包含一组请求 ID 队列。
3. TPC 按配置的并行数量执行多个发运计划。
4. 单个发运计划内部按队列顺序发送请求。
5. 如果计划达到超时时间，TPC 停止继续处理该计划后续请求。
6. 如果计划配置为遇错中断，则某个请求失败后，后续请求标记为异常并备注中断原因。

## 8. 功能需求

### 8.1 自动装配

- Starter 被业务系统引入后，应自动装配 TPC 所需的配置、注册中心、应用服务、持久化组件和可选控制接口。
- 应支持通过配置开关启用或关闭 TPC 能力。
- 应支持通过独立配置开关启用或关闭运维控制接口。

### 8.2 请求类型注册

- 业务系统可通过 Spring Bean 扩展请求类型。
- 每个请求类型必须具备唯一名称。
- 每个请求类型必须声明对应的第三方社群类型。
- 当请求类型名称重复时，系统启动应失败并提示冲突。
- 当请求发送时找不到请求类型，系统应抛出明确异常。

### 8.3 第三方社群注册

- 业务系统可通过 Spring Bean 扩展第三方社群。
- 每个第三方社群必须具备唯一社群类型和可读名称。
- 第三方社群负责根据请求选择发送器。
- 第三方社群可选择实现发运计划生成能力。
- 当社群类型重复时，系统启动应失败并提示冲突。
- 当请求发送时找不到社群，系统应抛出明确异常。

### 8.4 发送器注册

- 业务系统可通过 Spring Bean 扩展发送器。
- 每个发送器必须具备唯一名称。
- 发送器负责执行具体第三方调用并返回统一响应。
- 发送器可声明自身超时时间，默认超时时间为 30 秒。
- 发送器可通过回调逻辑判定业务成功或失败。
- 当发送器名称重复时，系统启动应失败并提示冲突。
- 当社群找不到目标发送器，系统应抛出明确异常。

### 8.5 请求状态管理

- 第三方请求状态至少包括 `WAIT`、`STAND_BY`、`RECEIVED`、`COMPLETED`、`ERROR`。
- 新建请求默认进入 `WAIT`。
- 只有 `WAIT` 状态请求允许进入发送准备阶段。
- 请求进入发送准备阶段时，状态变更为 `STAND_BY`，执行次数加 1，并记录最后执行时间。
- 收到第三方响应后，状态变更为 `RECEIVED`。
- 回调处理完成后，状态变更为 `COMPLETED`。
- 发生异常时，状态变更为 `ERROR`。
- 支持将指定请求重置为 `WAIT`，用于人工修复后重新发送。
- 支持人工设置请求状态；设置为 `COMPLETED` 时业务成功标记为 true，其余状态业务成功标记为 false。

### 8.6 请求重发

- 支持按请求 ID 批量重发请求。
- 只有 `WAIT` 状态请求允许重发。
- 重发请求使用同步发送模式。
- 非 `WAIT` 状态请求重发时，应返回明确业务异常。

### 8.7 投递结果留痕

- 每次发送后均需生成一条投递结果。
- 投递结果应记录结果 ID、发运计划 ID、第三方社群名称、社群类型、发送器名称、请求 ID、响应是否成功、响应编码、响应数据类型、响应数据、异常阶段和异常消息。
- 投递结果应支持按请求 ID 查询和问题排查。
- 投递结果保存失败时，不应覆盖请求状态保存错误，应分别记录日志。

### 8.8 运维控制接口

第一阶段提供以下运维接口能力：

| 能力 | 说明 |
|------|------|
| 重置为待发送 | 将指定请求批量重置为 `WAIT` |
| 重发请求 | 对指定 `WAIT` 请求批量执行同步重发 |
| 人工设置状态 | 将指定请求批量设置为指定状态，并同步维护业务成功标记 |

运维控制接口应由配置开关控制，避免生产环境误暴露。

### 8.9 持久化

- TPC 应持久化第三方请求。
- TPC 应持久化投递结果。
- TPC 应支持请求载荷以 JSON 形式保存。
- TPC 应保存请求载荷的类型信息，以支持恢复为业务请求模型。
- TPC 应支持请求状态、请求类型、请求 ID 等常用查询索引。

## 9. 数据需求

### 9.1 第三方请求

第三方请求至少包含：

- 请求 ID
- 请求类型
- 请求载荷
- 请求载荷类型
- 请求状态
- 版本号
- 请求时间
- 最后执行时间
- 执行次数
- 业务成功标记
- 备注
- 创建人、创建时间、更新人、更新时间

### 9.2 投递结果

投递结果至少包含：

- 投递结果 ID
- 发运计划 ID
- 第三方社群名称
- 第三方社群类型
- 发送器名称
- 请求 ID
- 响应成功标记
- 响应编码
- 响应数据类型
- 响应数据
- 异常阶段
- 异常消息
- 创建人、创建时间、更新人、更新时间

## 10. 配置需求

| 配置项 | 说明 |
|--------|------|
| `enigma.tpc.enabled` | 是否启用 TPC Starter |
| `enigma.tpc.request-enabled` | 是否启用 TPC 请求运维控制接口 |

配置命名在 Enigma 实现中应统一使用 `enigma.tpc` 前缀；参考项目中的 `dcs.tpc` 仅作为功能参考。

## 11. 验收标准

- 引入 Starter 后，业务系统能够通过 Spring Bean 注册请求类型、第三方社群和发送器。
- 重复注册请求类型、第三方社群或发送器时，系统启动失败并提示重复项。
- 创建请求后，请求默认处于 `WAIT` 状态，执行次数为 0。
- 同步发送成功后，请求依次完成 `WAIT -> STAND_BY -> RECEIVED -> COMPLETED` 状态流转，并保存投递结果。
- 发送异常后，请求进入 `ERROR` 状态，并保存包含异常阶段和异常消息的投递结果。
- 异步发送模式立即返回受理结果，后台完成请求发送和结果保存。
- 发送器超时时，系统保存超时结果，错误编码可区分普通异常和超时。
- 批量发运计划支持并行执行多个计划，单个计划内部按请求队列顺序执行。
- 配置遇错中断时，发运计划在失败后不再继续正常发送后续请求。
- 运维控制接口可按配置启用或关闭。
- 重发接口只允许重发 `WAIT` 状态请求。
- 人工设置 `COMPLETED` 状态时业务成功标记为 true，设置其他状态时业务成功标记为 false。

## 12. 待确认问题

- 第一阶段是否需要提供查询接口，还是仅提供应用服务能力给业务系统自行封装。
- 第一阶段是否需要内置 MyBatis 持久化实现，还是只定义 Repository 契约和可选实现。
- 第三方请求 ID 是否由 TPC 统一生成，还是由业务系统传入。
- 投递结果是否需要支持按第三方社群、发送器、状态和时间范围分页查询。
- 发运计划是否需要持久化计划本身，还是只在投递结果中记录计划 ID。
- 运维控制接口是否需要增加权限注解或仅依赖业务系统网关控制。
